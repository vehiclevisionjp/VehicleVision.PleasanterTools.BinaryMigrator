# リリース手順

## 版

版の単一情報源は `Directory.Build.props` の `VersionPrefix`。セマンティックバージョニングに従い、1.0.0 未満は互換を保証しない。

## 手順

1. `develop` で `VersionPrefix` を上げ、`master` へ PR を出してマージする
2. Actions の「リリースタグ作成」を `master` から実行する。最初は `dry_run` のまま版だけを検証する
3. 問題なければ `dry_run` を外して実行する。必須チェックの成功を確認してから、GitHub App のトークンで `vX.Y.Z` タグを作る
4. タグを契機に「Release」ワークフローが、検証、配布 ZIP と SHA-256 の作成、GitHub Releases への公開を行う。あわせて NuGet パッケージ（dotnet tool）を作り、nuget.org へ公開する（下の「NuGet で公開する」）

`vX.Y.Z-rc.1` のようにハイフン付きの版はプレリリースとして公開する。

## NuGet で公開する

CLI を **dotnet tool** として nuget.org へ公開する。配布 ZIP と GitHub Releases の流れはそのままで、NuGet は追加の配布経路である。

| 項目 | 値 |
| --- | --- |
| パッケージ ID | `VehicleVision.PleasanterTools.BinaryMigrator`（Cli のアセンブリ名と同じ） |
| コマンド名 | `pleasanter-binary-migrator`（`ToolCommandName`） |
| 形 | RID 非依存（framework-dependent）の単一パッケージ。**.NET 10 ランタイムが要る** |
| 含めるもの | Cli と Core の実行物、依存 DLL、README・LICENSING.md・LICENSE・LICENSE-COMMERCIAL.md・NOTICE。pdb は含めない |
| Core | 別パッケージにしない（`IsPackable=false`）。Cli の出力に含まれる |

利用者は次で入れる。

```bash
dotnet tool install --global VehicleVision.PleasanterTools.BinaryMigrator
pleasanter-binary-migrator --help
```

### nuget.org の準備（初回。管理者の作業）

公開は **Trusted Publishing**（GitHub Actions の OIDC）。長期の API キーは持たない。`release.yml` の `publish-nuget` ジョブが、NuGet/login で 1 時間有効の API キーを受け取って push する。

1. 組織の変数 `NUGET_ORG_USER`（公開用の共用アカウントの nuget.org プロフィール名。メールアドレスではない）を、このリポジトリへ共有する。未設定だと `publish-nuget` が明確なエラーで止まる
2. nuget.org の Trusted Publishing に、次のポリシーを登録する（未公開のパッケージ ID は、ポリシーに Glob を入れて初回の push で作る）

   | 項目 | 値 |
   | --- | --- |
   | Package Owner | 組織 `vehiclevisionjp` |
   | Repository Owner | `vehiclevisionjp` |
   | Repository | `VehicleVision.PleasanterTools.BinaryMigrator` |
   | Workflow File | `release.yml` |
   | Environment | 空 |
   | Scopes | Push new packages and package versions |
   | Glob | `VehicleVision.PleasanterTools.BinaryMigrator` |

**準備が無いままタグを作ると、GitHub Release は出て、NuGet だけ失敗する。** タグは付け直せないので、準備を済ませてからタグを作る。

### 版と公開の流れ

- nupkg の版はタグから `v` を除いた値（`-p:Version`）。`release-check.ps1` が、タグと `VersionPrefix` の一致と、タグのコミットが `master` に含まれることを検査する。`publish-nuget` は、nupkg の版がタグと一致することも確かめる
- `verify` ジョブが `dotnet pack` と nupkg の内容確認（必要なファイルがあること、pdb などが無いこと）まで行い、nupkg を artifact に残す。PR と dry-run でもここまで動くので、pack の不備は公開の前に分かる
- `publish-nuget`（nuget.org へ push）と `publish`（GitHub Release）は、タグの push か `dry_run=false` の dispatch のときだけ動く。dry-run では動かない
- **公開した版は取り消せない。** nuget.org では削除できず、非推奨にできるだけ。タグも付け直せない。同じ版の再実行は `--skip-duplicate` で害がない
- patch 更新の自動リリース（`patch-release.yml` → `release-run.yml`）も、同じ `release.yml` を通るため、準備が済むと **自動でも nuget.org へ公開される**

### 初回は dry-run を両方回す

`release.yml` の公開ジョブは、タグの push でしか完全には動かない。初回は次の 2 つの dry-run を、どちらも回して確かめる。

```bash
# リリースタグ作成（版・起動ブランチの検査だけ。タグは作らない）
gh workflow run release-run.yml --ref master -f dry_run=true
# Release（verify まで。pack と nupkg の確認が動き、公開ジョブは動かない）
gh workflow run release.yml --ref develop -f dry_run=true
```

`release.yml` の dry-run が緑で、`NuGet パッケージ` の artifact に nupkg が残ることを確認してから、タグを作る。

## 公開前の確認

- `LICENSE` と `NOTICE` が現状と合っている
- 配布物に設定ファイル・秘密・参照ソース・Git メタデータが入っていない（`scripts/package.ps1` が検査する。nupkg は `release.yml` の verify が検査する）
- NuGet で公開する前に、nupkg が同梱する依存のライセンスを確認する。特に Microsoft.Data.SqlClient が伴う SNI（Microsoft 独自の許諾。`runtimes/win-*/native/` に入る）は、NOTICE と LICENSING.md の「例外」の節に条件がある（nupkg にも同梱される）。nuget.org 公開はこの頒布にあたるので、公開前に確認する
- 参照ソースは必要時の事実確認専用であり、リリース CI では取得しない。
  共有先を含めてビルドから隔離し、調査の根拠は文書の完全な SHA・固定リンク・参照日で確認する
- 商用公開でデュアルライセンスにする場合は [ライセンス](ライセンス.md) の手順が済んでいる
